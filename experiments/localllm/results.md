補足:

- 同一プロンプト再送時は Ollama のプロンプトキャッシュが効き、prompt eval rate が 150-290 tok/s に跳ねる（qwen r2/r3: 153/165, gpt-oss r3/r4: 279/287, gemma r2/r3: 72/73）。上表の P-short コールド値が実 prefill 速度
- prompt_eval_count がモデルごとに異なるのはトークナイザ差（同一ファイルで 1736〜1961 tok）
- gpt-oss:20b は `"think": false` を指定しても推論チャンネルが生成され、num_predict 以内だと `response` が空になる。**実用上は `think:"low"` が下限** → teaspoon-ide 側に対応済み（後述 §3 注記）
- 余談: qwen3.5:4b に `think:"low"` を送ると エラーにならず**思考ONとして処理**される。レベル非対応モデルへのレベル指定はサイレントに意味が変わるので注意

## 3. teaspoon-ide 実タスク

未実施。以下の観察が事前知見として得られた:

- gpt-oss:20b の `think` 制御の癖 → **teaspoon-ide 側で対応済み**（2026-10-17, Unreleased）。Settings の Thinking に Low/Medium/High を追加し、モデル適合しない値は送信前に変換（レベル→boolean-only モデルは low→off/medium,high→on、gpt-oss の off→low）。qwen3.5 系は `Off`、gpt-oss は `Low`（`Off` でも自動で low に降格）、gemma4 系は `Model default` で運用する
- P-long（~1800 tok）1ターンあたり prefill だけで 67s (gpt-oss) / 84s (qwen) / 149s (gemma)。5ステップのループで prefill だけ 5-12分 — **自律ループの律速は全モデルで prefill** という設計書の予測を裏付け

### タスク定義（詳細・固定プロンプト文は `bench/tasks.md`、対象は `bench/fixture/`）

| ID | タスク内容 | 想定ステップ数 |

| T3 | pytest 1件失敗の原因調査→修正→再実行確認 | 4-5 |

## 5. 所感・結論

- 設計書の予測「dense を小さくするより MoE のアクティブを小さくする」は速度面では確認できたが、**本命だった gpt-oss は実タスクで失格**: harmony の commentary チャンネルにコマンド意図を逃がし、`/api/chat` の content が空になる。平文コマンドプロトコルとは非互換（prompt 押し込み・few-shot・think 全設定で回避不能）。速度≠使える、を地で行く結果
- **gemma4:e4b が実質優勝**: 全タスク形式崩れなし・T3 をちょうど 5step で完走・デコード最速。e4b は今回の計測対象で唯一「速度・形式・正しさ」を全て満たした
- qwen3.5:9b の hybrid attention は本物 — context を伸ばしてもデコードが落ちない（4.49→4.38）。対して gemma4:12b は 6.88→3.11 と半減
- qwen3.5:4b は速度こそ基準越えだが、簡単な読解タスクで既に幻視（存在しない export の列挙）＋実タスクでも出力誤読・テスト文言の幻視。「4B以下は単発向け」の設計書評価を裏付け
- ただし絶対値として prefill 13-39 tok/s は、エージェントループ（毎ターン全履歴を再処理）ではどのモデルでも体感が重い。`num_thread=4` 制限なので全コア使用なら ~1.5倍の余地はある
- 副産物: teaspoon-ide に think レベル選択・モデル適合マッピング・num_ctx 設定を実装（Unreleased）。num_ctx 未指定(4096)はループ系で枯渇リスクがあるため Settings で 8192 を推奨

## 6. まとめ（2026-10-17 時点）

- **推奨ローカルモデル: `gemma4:e4b`** — デコード最速（~7.4-8.0 tok/s）・完全決定的・テキストコマンドを一度も崩さず・T3 を5step完走。CPU 環境の自律ループとして現実解
- **第2候補: `qwen3.5:9b`** — ループは回る（T3完走）がデコード 4.5 tok/s が基準未満＋幻視癖あり。num_thread 全開なら実用ラインに届くかも
- **非推奨: `gpt-oss:20b`** — 速度は良いが commentary チャンネル仕様でテキストコマンドを出せない。単発チャット用途ならあり
- **非推奨（ループ用途）: `gemma4:12b`・`qwen3.5:4b`** — 前者は長コンテキストでデコード半減。後者は明示された修正タスク（T3）は完走できるが、**自発的な判断が絡む場面で破綻**: T1 は出力誤読+幻視、T2 は「変更するな」と認識しつつスコープ外を修正。結果をユーザーの監督なしに信用できない

## 付録A: `num_ctx` 4096→8192 の影響（記事化用メモ）

| 観点 | 影響 |
|---|---|
| モデルの知能 | **変わらない**。重みは同じ。変わるのは「見える履歴の量」だけ |
| ループの成功率 | **実質上がる**。4096 だとシステムプロンプト+ファイル読解+履歴ですぐ溢れ、Ollama は古い内容を黙って捨てる（＝モデルの記憶喪失）。8192 なら多くのターンが収まる |
| メモリ | KV cache が**実際に使った分だけ**増える。9B級で 8k フル使用でも +1〜2GB 程度。30GB RAM なら誤差範囲。qwen3.5 の hybrid attention は KV が元々小さいのでさらに軽い |
| CPU 速度 | **設定値自体は速度に直接効かない**。prefill は実際のプロンプト長比例なので、同じターンなら 4096 でも 8192 でも同速。ただし 8192 を許すと履歴がより長く蓄積し後半ターンが遅くなる、という間接コストはある |

結論: CPU 環境でも 8192 は不利にならず、ループ信頼性を買う価値がある。design.md の「num_ctx は必要最小限」は「32k など無駄に大きくしない」意味で、**4096 はエージェント用途では小さすぎる下限**（gpt-oss 空応答の初動調査で一旦は有力容疑だったことが裏付け）。

なお teaspoon-ide では「モデル切替時に Context Size を既定（空欄）へリセット」を実装済み（Unreleased）。最適値がモデル依存のため、切替時に前の設定を引きずらない仕組み。
