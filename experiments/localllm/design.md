# ローカルLLMコーディング環境の設計考察

CPU-only・Ollama 前提のローカルLLMコーディング環境についての調査まとめ。
対象期間: 2026-10時点の公開情報。実証は別途行う。

## 0. 前提

- 実行環境: Windows + CPU のみ（GPUオフロードなし）
- ランタイム: Ollama（`qwen3.5:4b` / `qwen3.5:9b` pull 済み）
- 用途: teaspoon-ide 経由のコーディング補助・自律エージェントループ
- Bonsai 2（PrismML の ternary モデル）は **Ollama 未対応のため実証対象外** とする（後述）

## 1. CPU推論の特性（考察の土台）

| フェーズ | 律速要因 | モデル選びへの含意 |
|---|---|---|
| デコード（生成） | **メモリ帯域**（重みを毎トークン読む） | 重みサイズにほぼ比例して速い。量子化・ternary が効く |
| Prefill（プロンプト処理） | **計算量** | コンテキスト長にほぼ比例。小さい量子化では解決しない |
| コンテキスト維持 | KV cache サイズ | 長コンテキスト・エージェントループで累積する |

派生する結論:

- **デコード速度は「全パラメータ数」ではなく「1トークンあたりのアクティブパラメータ数」で決まる**
  → MoE（総量大・活性小）が CPU の攻略法。3〜4B アクティブの MoE は 4B dense 並みの速さで 20B+ 級の知能を出す
- **ハイブリッド attention（linear : full = 3:1）** は KV cache が約1/4になり、ループで履歴が膨らむ用途で劣化が緩い
- エージェントループは「大きな prefill + 短い生成」の直列繰り返し → **prefill の遅さが体感的ボトルネック** になりやすく、量子化だけでは解決しない

## 2. Bonsai 2（実証対象外・参考情報）

PrismML の Qwen3.5 ベース ternary（{−1,0,+1}）モデル。アーキテクチャは Qwen3.5 と同一で重みのみ圧縮。

| サイズ | 重み | 対Qwen3.5 retention（公式） |
|---|---|---|
| 2B | 0.43GB | Coding 115% / Knowledge 82.9% |
| 4B | 0.95–1.21GB | Coding 100.7% / Agentic(Tau2) 75.8% |
| 9B | 2.0–2.56GB | Coding 100.1% / Agentic 92.4% |

考察:

- **メリットは「フットプリント + 帯域律速のデコード高速化」**。CPU でも実利はある（Q4 の約1/3 → デコードも概ね比例して速い見込み）
- 公式の「5x throughput」は RTX 4090 / M5 Pro の数字で、x86 CPU の実測は未公開
- **コーディング retention は高いが、マルチステップ遂行（Tau2）で 4B は 75.8%** と落ちる。自律エージェント用途では Q4 の方が上の可能性
- 実行には Hadamard 変換対応ランタイムが必要（upstream llama.cpp b11555+ は Q2_0 版のみ、PQ2_0/PTQ1_0 は PrismML 独自バイナリ）。**Ollama 経由では現状動かない**ため本検証から除外

## 3. 候補モデル（実証対象）

### dense 9B クラス

| モデル | Q4サイズ | 特徴 | 見通し |
|---|---|---|---|
| `qwen3.5:9b` | 6.6GB | Gated DeltaNet ハイブリッド attention（KV cache 小）・262K ctx・vision対応・LCB v6 ~85 | **本クラスの本命**。ただしサンプリング分散が大きい報告あり（後述） |
| `gemma4:12b` (QAT) | ~7.2GB | dense では収まりがいい。外部実測で出力分散が最小（22/22×3連続） | 安定性重視なら検証価値あり |
| `qwen2.5-coder:7b` / `:14b` | ~4.5 / 9GB | コード特化の実績ある旧世代 | 14b は CPU では重い |

### MoE 系（RAM に余裕がある場合の本命）

| モデル | Q4サイズ | アクティブ | 特徴 |
|---|---|---|---|
| `gpt-oss:20b` | ~13GB | ~3.6B | tool use・エージェント系に強い。Ollama 標準対応で最も手軽。RAM 16GB 級の上限 |
| `qwen3:30b-a3b` / `qwen3.5:35b-a3b` | ~18GB | ~3B | デコードは 3B 級の速さで 30B 級の出力。RAM 32GB+ なら最強格 |
| `gemma4:26b` (26B-A4B) | ~15GB | ~4B | 推論特化（AIME系に強い）。コーディング専用ではない |

### 除外・見送り

- Bonsai 2 全サイズ: Ollama 非対応
- `devstral-small:24b`: CPU では重すぎる
- 2B クラス: Knowledge retention が低くコーディング用途に非推奨

## 4. teaspoon-ide 自律ループの見通し

自律エージェントコーディングが CPU で厳しいのは、**量子化ではなく以下が主因**:

1. **直列レイテンシ**: ループ1ターン = 大きな prefill + 生成。10ステップ踏むと待ち時間が致命的
2. **フォーマット遵守**: teaspoon-ide は独自の `// GREP:` / `// READ_FILE:` コマンド形式に依存。小さいモデルはここが一番壊れやすい（作者自身も TODO に挙げている）
3. **能力の下限**: 自律ループの現実的な下限は **9B 級**。4B 以下は単発タスク向け

実用域の切り分け:

| 用途 | 4B級 | 9B級 | MoE 20B+ |
|---|---|---|---|
| チャット・単発生成 | ○ | ○ | ○ |
| 対話的コーディング補助 | △ | ○ | ○ |
| 自律エージェントループ | × | △（要検証） | ○候補 |

## 5. 実証計画

### 計測項目

- `ollama run --verbose` 等で **prompt eval rate / eval rate (tok/s)** を記録
- teaspoon-ide 実タスクでの成功率（フォーマット遵守・ループ完走・編集の正しさ）
- 同一プロンプト複数回での**出力分散**（qwen3.5系で不安定の報告があるため）

### 推奨設定

- `think:false` 固定 + 低温度（~0.2）。thinking の思考トレースは CPU では最大のコスト
- `num_ctx` は必要最小限に（KV cache・prefill 両方に効く）
- Ollama の `num_thread` を全コア未満に制限して他作業を阻害しない（teaspoon-ide v1.2+ の CPU Threads 設定）

### 検証順序

1. `qwen3.5:9b`（pull済・本命）
2. `gpt-oss:20b`（MoE・RAMが許せば最有力対抗）
3. `gemma4:12b`（dense・安定性検証）
4. RAM 32GB 以上ある場合のみ `qwen3:30b-a3b` 系

### 判定基準（案）

- デコード 5 tok/s 以上 = 対話的補助として実用域
- teaspoon-ide の自律ループが **5ステップ以内のタスクを完走** できれば「そこそこ動く」合格ライン

## 6. 結論

- dense 9B を量子化で小さくする方向ではなく、**同じメモリで MoE のアクティブパラメータを小さくする**方向が CPU の正攻法
- `qwen3.5:9b` はハイブリッド attention のおかげで本クラスでは最有力。まずこれを評価するのが最短
- 自律エージェントを本気で回したければ、ローカルに拘らず Gemini Flash 系 BYOK（teaspoon-ide の本命想定）か、ローカルなら MoE 20B+ 級が現実解

## 付録: 用語メモ（記事化用）

| 用語 | 説明 |
|---|---|
| **dense（密）モデル** | 全パラメータが毎トークンの計算に使われる通常の構造。9B dense なら生成のたびに 9B 全てを読みに行く。シンプルだがCPUでは重い |
| **MoE（Mixture of Experts）** | 層内の「専門家」サブネットをトークンごとに数個だけ起動する構造。総パラメータは大きいが計算に使うのは一部だけ |
| **アクティブパラメータ** | MoE で1トークン生成に実際に動くパラメータ量。「30B-A3B」は総量30B・活性3Bの意味。CPUの生成速度は全量ではなくこちらでほぼ決まる |
| **量子化（quantization）** | 重みの精度を落として小さくする手法。`Q4_K_M` は約4bit/重み、`Q2_0` は約2bit。小さいほど速く軽いが品質が下がる |
| **ternary（3値）** | 重みを {−1, 0, +1} の3値だけにする極端な量子化（Bonsai 2 が採用）。約2bit以下の表現で済むため劇的に小さい |
| **prefill（プロンプト処理）** | 入力トークンをまとめて内部表現にする最初の処理。計算律速で、エージェントループの待ち時間の主犯 |
| **decode（生成）** | 1トークンずつ出力を続ける処理。メモリ帯域律速で、重みが小さいほど速い |
| **tok/s** | 1秒あたりの生成トークン数。CPU実用の目安は 5 tok/s 前後〜 |
| **KV cache** | 過去トークンの中間表現のキャッシュ。コンテキストを伸ばすほどメモリを食い、速度も落ちる |
| **ハイブリッド attention** | 通常のattention層と線形attention（DeltaNet等）を混ぜた構造。Qwen3.5/Gemma4系で採用され、KV cache が小さく長コンテキストに強い |
| **thinking モード** | 回答前に推論トレースを数千トークン生成する動作。精度は上がるがCPUでは時間がかかる。`think:false` で切れる |
| **GGUF** | llama.cpp 系で使う単一ファイルのモデル形式。Ollama も内部でこれを使う |
| **エージェントループ** | LLM が「ファイル読む→考える→編集する→結果を見る」を複数ターン自律で回す動作。フォーマット遵守と長いコンテキスト処理が要求される |
| **BYOK** | Bring Your Own Key。ツールは無料だがAPIキーは自分で用意して従量課金する方式（teaspoon-ide + Gemini の想定形態） |
