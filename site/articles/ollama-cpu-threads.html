トークンは届いているのに画面に出ない — ローカルLLMのCPU割り当てを絞ると「体感速度」はむしろ上がった（新版Ollamaでは事情が変わっていた）

公開実験ノート | 計測: 2026-10

ローカルLLMをIDEに組み込んでいて、ある奇妙な現象に気づきました。全コアを生成に回す設定のほうが、ストリーミング表示がカクついて体感は遅いのです。トークン自体は届いているのに、画面への反映が遅れる。今回これを「ワイヤ到着時刻」と「DOM表示時刻」を別々に採る計測で定量化しました — そして検証の途中でOllamaを最新版に上げたところ、現象の構造ごと変わっていることが分かりました。2部構成で記録します。

前提: 計測したいのは「生成速度」ではない

APIのtok/sを測るだけなら簡単ですが、今回測りたいのは 「APIから返ったものを表示しきるまでの速度」 です。つまり:

  • 全コア使用: LLMがCPUを張り付かせ、レンダラ（画面描画側）がCPUを奪われて、届いたトークンが表示に追いつかない
  • コア数を絞る: 生成速度はほぼ同じなのに、表示・操作が滑らかで体感はむしろ速い

この仮説を、Teaspoon IDE（当サイト運営者の自作IDE、Electron製）の「CPU Threads」設定を通して実測しました。この機能は本記事に合わせて v1.2.0 として公開されています。

計測方法: ワイヤ側と画面側を別々に時刻を採る

  • 計測プロキシ: アプリとOllamaの間に薄いプロキシを挟み、NDJSONチャンクごとのワイヤ到着時刻を記録。レンダラが飢餓してもプロキシ側の時計は正確
  • DOM表示時刻: MutationObserverでストリーミング表示文字数を逐次記録 → 各チャンクの「到着→表示」の遅延（lag）が出る
  • イベントループ遅延: 100ms周期のsetTimeoutドリフトを計測（UIスレッドの逼迫度）
  • 実効FPS: requestAnimationFrameの発火回数
  • UI操作プローブ: 生成中・prefill中に実際のUIボタン（チャットフォーカス切替）をクリックして応答時間を計測
  • 条件固定: temperature 0・seed固定・num_predict 600・think:false で出力を揃える

環境: Ryzen 5 4500U（6論理コア）・CPU推論・Windows。スレッド数は「全コア相当」と「4」を比較。60秒の計測窓で採取した値の中央値。計測スクリプトは Teaspoon IDE リポジトリの e2e/bench-threads.mjs（Playwright + 計測プロキシ）。

第1部: Ollama 0.21.0 — 生成速度は同じ、届いてから見えるまでが90倍違う

まず当時の環境（Ollama 0.21.0・qwen3.5:4b Q4_K_M・「未指定=全コア」対「4コア」、有効ラン n=2）で取れた数字です:

指標全6コア4コア
ワイヤ到着速度（生成速度相当）4.6 chars/s4.7 chars/s
表示遅延 P95（到着→DOM反映）181 ms2 ms
表示遅延 Max553 ms6 ms
イベントループ遅延 P9570 ms13.6 ms
実効FPS55.960.0
UI操作応答（実クリック）929 ms158 ms

ハイライトは3つ:

  1. 生成速度はまったく同じ — 4.6 vs 4.7 chars/s。デコードはメモリ帯域律速なので、6→4スレッドでもトークン生産は落ちませんでした
  2. 表示遅延がP95で181ms→2ms（約90倍差） — 全コアでは届いたトークンが画面に出るまで最大0.55秒待たされます。ストリーミング表示が「追いつかず溜まる」状態です
  3. UI操作1回が929ms→158ms（約6倍） — 「LLMが回っている間にブラウザ操作やスクショ等の軽作業ができるか」の代理指標です

つまり全コア使用は「届いているのに見えない」状態を作り、4コアは同じ生成速度のまま「届いたものが即座に見え、操作も効く」状態を作ります。体感で「4コアのほうが速い」のは錯覚ではなく、表示パイプラインの遅延として実在しました — 旧エンジンのrunnerは生成中、実測で約5.7コアを占有し続けていました。

第2部: Ollama 0.40.2 — 最新版に更新したら、前提が変わっていた

記事公開前に「0.21.0は古いのでは」と気づき、最新の 0.40.2 に更新して再計測しました。すると差がほぼ消えました:

指標num_thread=6num_thread=4
ワイヤ到着速度7.6 chars/s7.5 chars/s
表示遅延 P9513 ms3 ms
表示遅延 Max48 ms10 ms
イベントループ遅延 P9514.2 ms13.9 ms
実効FPS59.959.9
UI操作応答123 ms114 ms

Ollama 0.40.2・qwen3.5:4b・有効ラン n=3。なお0.40.2では「未指定」の挙動が変わったため（後述）、比較は明示的な num_thread=6 対 4 に変更しています。9.6GBの gemma4:e4b でも同様に差は出ませんでした（lagP95: 5ms vs 3ms）。

なぜ消えたのか、runnerプロセスを調べると内部構造が変わっていました:

Ollama 0.21.0Ollama 0.40.2
runner実装ollama runner（旧エンジン）llama-server（llama.cpp本体）
スレッド未指定時全コア（=6）n_threads=3（ログ実測）
num_thread=6 の実CPU約5.7コア占有約4.3〜4.6コア（飽和しない）
qwen3.5:4b 生成速度約4.7 tok/s相当約6.5 tok/s

読み取れること:

  • デフォルトが変わった: 0.40.2では未指定=「3スレッド」。そもそも全コア占有しなくなっています
  • 明示しても飽和しない: num_thread=6（内部 n_threads=6 確認済み）でも実効は約4.3〜4.6コア止まり。decodeがメモリ帯域律速で、新エンジンはスレッドが待ちで止まる設計になったようです
  • 余剰が生まれた: 常時1.5〜2コア分の空きがあるので、レンダラ・OS・他アプリが割り込める = UI飢餓が起きない
  • prefillも同様: プロンプト処理（計算律速）の間もUI応答は90〜180ms程度で、飢餓は再現しませんでした

ユーザーが体験した「全コアでカクつく」は0.21.0の旧エンジンがCPUを全力回転する設計だったことによる実在の現象で、新版ではエンジン側が解消していました。

では「コア数指定」は無意味になったのか — そうではない

新版で差が出なくても、この設定には2つの価値が残ります:

  1. 挙動の「保証」: デフォルト・エンジン内部のスレッド管理はバージョンごとに変わります（実際、0.21→0.40で未指定が6→3に変わった）。num_thread は「これ以上は使わせない」という上限を、バージョンやモデルに関わらず確定させるスイッチです。将来のOllama・他のモデル・他の重い処理との共存時に、上限があるのと無いのでは安心感が違います
  2. APIの到達範囲: そもそもこのオプションはOllamaネイティブの /api/chat にしか存在しません（後述）

もう1つの収穫: 「Thinking」のON/OFF

計測中に気づいた副産物です。使用モデル（qwen3.5:4b）はthinking系モデルで、ollama run で「こんにちは」と打つだけで「入力の分析→挨拶案の列挙→自然さの推敲→言語確認」という長い思考トレースを生成してから返答します。重いPCではこれだけで数十秒〜数分が消えます。

OllamaのネイティブAPIには think フラグがあり、think:false を送れば思考トレースを抑制できます（今回の計測では preContentChunks=0 を確認済み＝思考チャンクは一切来ていない）。Teaspoon IDEはこの ON/OFF を設定画面から切り替えられるようにしました。ローカルLLMの実用速度という意味では、これはコア数指定と並ぶ効き目のあるスイッチです。

ここがツールの差になる: OpenAI互換APIでは渡せない

実装上の要点は、これらのオプションが Ollamaネイティブの /api/chat にしか存在しない ことです。

やりたいことOllama /api/chatOpenAI互換 /v1
CPUコア数の上限指定options.num_thread で可渡す術がない
ThinkingのON/OFFthink で可渡す術がない
出力長・seed固定等options.*一部のみ

ClineをはじめとするVS Code拡張系の多くは、ローカルLLMの「CPU割り当てコア数」を設定項目として持っていません。APIの形が違うため、そもそも渡すチャネルがないのです。ローカルLLMを「モデルを動かす」だけでなく「PCを殺さず動かす」ためには、ネイティブAPIのオプションまで届く設計が必要でした — Teaspoon IDEが /api/chat へ移行した理由がこれです。

教訓

  • tok/sは体験の半分しか説明しない: 生成速度が同じでも、表示側が飢餓すれば体感は激変する（旧エンジンでは実測90倍差）
  • 「全部使う」は常に最適ではない: ただし「どれだけ使うか」はエンジンの内部実装次第で、バージョンで挙動が変わる
  • 検証は最新環境でもやり直す: 今回「新版で再現しない」ことを確認したおかげで、現象がエンジン依存であることが分かり、記事の説得力が上がった
  • UIの応答性も計測対象にできる: ワイヤ時刻とDOM時刻を分けて採れば「体感の遅さ」は定量化できる
  • ローカルLLM機能はAPI到達範囲で決まる: 互換APIの共通部分しか使えない設計だと、num_threadやthinkのような実用スイッチを実装できない

計測スクリプトは Teaspoon IDE リポジトリの e2e/bench-threads.mjs（Playwright + 計測プロキシ）、生データは e2e/bench-threads-results.json にあります。BENCH_THREADS=6,4 BENCH_RUNS=3 BENCH_MODEL=qwen3.5:4b node e2e/bench-threads.mjs で再現できます。
