I thought "the model was weak" — it was my own app's bug. How local-LLM measurement exposed a harness design flaw

Public experiment note | Measured: 2026-10 | Series: CPU-only local-LLM coding | Difficulty: Intermediate

I've been embedding local LLMs into my own IDE (Teaspoon IDE) and measuring coding-agent performance in a CPU-only environment.

Along the way I kept observing symptoms like "this model has a weak memory" and "it re-reads the same file over and over." Those turned out not to be model weaknesses — they were a bug in my own harness. This is that record.

How it started: a strange failure in qwen3.5:4b

I gave the small 4B model a task (T3): "fix one failing test and confirm everything passes."

On the old harness (v1.5.0), this is what happened:

  1. READ_FILE: test_calc.py — reads it
  2. READ_FILE: calc.py — reads it
  3. READ_FILE: test_calc.py — reads it again. Response: "unchanged — use the content you already read"
  4. The model says: "I read them, but the contents aren't visible here"
  5. Tries GREP, gets 0 hits → re-reads again → exhausts all 6 turns and fails

It's told "unchanged," yet insists "I can't see the contents." At first I assumed the 4B simply lacked the comprehension.

Investigation: tool results survived only one turn

Tracing the code revealed a design flaw.

The history sent to the model in the agent loop (historyForRequest) accumulated user messages and assistant replies. But "tool execution results" — READ_FILE contents, command output — existed in context only for the immediately following turn, and were absent from history in every turn after that.

In other words:

  • Step 1 reads the file → in step 2 the content is in context → everything works
  • From step 3 onward, that content has already vanished from context
  • The duplicate-read suppression message "unchanged — use what you have" was pointing at content the model didn't have

The model's "I can't see the contents" was an accurate status report.

Implication: past evaluations needed reinterpreting

Knowing about this flaw changes how earlier measurements look.

I had rated the 9B model as "redundantly re-reading files" on the old harness (2 of 7 steps wasted). That was likely not "weak memory" but a legitimate self-repair — retrieving content that had disappeared. In other words, the smarter models were devising workarounds for my bug.

The fix

I made each step's tool-result prompt persist into the running history. Tool results now stay in context for the entire run, and the "unchanged" response finally becomes true.

I also fixed a second problem this experiment exposed — models wrapping entire search patterns in quotes (e.g. GREP "member.*discount", where the literal " ended up in the regex and matched nothing). The parser now strips outer quotes.

Control experiment: same model, same task, only the fix differs

ConditionResult
4b · old harness (T3-2)Consumed all 6 turns · stuck in re-read loop · unfinished
4b · fixed (T3-3)Completed in 5 turns (shortest path: pytest → read → fix → re-verify · correct)
9b · old harness (T3-2)Completed in 3 turns (batching reads into one turn dodged the bug by accident)
9b · fixed (T3-3)Completed in 3 turns (zero re-reads · shortest path)
e4b · fixed (T3-3)Completed in 4 turns (zero re-reads · no format breakage)

The same model went from "broken" to "clean shortest-path completion" — just by fixing the harness. And the 9b dropped from 7 steps (with 2 re-reads) on the old harness to 3 steps — the re-reading really did vanish.

Lessons

  1. "Model weakness" and "harness weakness" must be evaluated separately: articles claiming "this model is useless" may be rating the harness's constraints along with the model. If you build tools, suspect what's actually in the context before suspecting the model
  1. Design dedup and context-saving against what the model can actually see: "it read it before, so it must have it" is only true when that content is really present in the context
  1. Weak-model behavior is worth watching precisely because it's weak: a borderline 4B model has no slack, so it faithfully visualizes harness flaws. The strong models papered over the defect with self-repair — the weak one exposed it

About the implementation

The fix shipped as Teaspoon IDE v1.5.1 (see the CHANGELOG for details). The command protocol, history management, and feedback injection live in src/components/Chat.tsx and under src/services/.
