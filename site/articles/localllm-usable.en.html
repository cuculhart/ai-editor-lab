For those who thought "local LLMs can't be practical" — a coding agent measured with nothing but numbers, on CPU alone

Public experiment note | Measured: 2026-10 | Series: CPU-only local-LLM coding | Difficulty: Beginner

"Local LLMs are slow and not accurate enough. Compared to web Claude/GPT, they're useless."

I think that's true — if you expect them to work the same way as the web versions.

But there are workplaces where source code simply cannot be sent to an external service. Contracts forbid it, internal rules prohibit it, or you simply don't want your code becoming someone's training data. Saying "then we have to give up on AI assistance" just removes one option.

This article is a record of actually measuring how far a local-LLM coding agent can go on an ordinary PC with no GPU — CPU only. I report the good results and the bad ones alike.

Experimental conditions (all public)

ItemValue
CPUAMD Ryzen 5 4500U (6 cores, no SMT — an older laptop-class CPU)
GPUNone (integrated graphics present, but inference is CPU-only)
Memory32 GB (~22 GB free during measurement)
RuntimeOllama 0.40.2 + my own IDE "Teaspoon IDE"
LimitOnly 4 CPU threads for inference (leaving 2 cores for the OS and IDE)

I measured two things: speed (token generation rate) and real-task success rate (can it autonomously loop through file operations → edits → test runs).

The reality these numbers show:

  • Top speed is 8 tok/s. Genuinely slow compared to the tens of tokens per second of web APIs
  • An agent "thinking" for one turn takes 30 seconds to 2.5 minutes. One task end-to-end takes 3–7 minutes
  • And yet — a model exists that can carry the full sequence to completion: read the file, diagnose the cause, apply the correct fix, run the tests, and confirm

It's not "snappy like a chat." But if the shape is "do other work while you wait" or "have a consultant for code you can't send out," it's already practical.

Counter-intuitive discoveries

Almost every expectation I had going in was overturned:

  1. "Bigger file = smarter" does not hold. gemma4:e4b (9.6 GB) has a larger file than gemma4:12b (8.0 GB), yet it's faster and more accurate. e4b has a special efficiency-oriented architecture — the expectation that "e4b is a lightweight variant, so it must be weaker" was completely wrong
  1. "More parameters = better" doesn't hold either. The 9B model was more accurate than the 4B, but too slow to cross the practicality line. The 4B is fast but unreliable on correctness. e4b sat at the intersection of fast × correct
  1. Half of what looked like "model weakness" was my own app's bug. Symptoms like "re-reading the same file over and over" and "forgetting content it just read" were a design flaw where the tool wasn't properly keeping history in the model's context. After the fix, the same model completed tasks by the shortest path (details in part 3)

What "usable" means from a security standpoint

For a workplace that can't send code to a web AI, a local LLM being "usable" means:

  • Zero data leaves the machine: source code, designs, customer data, failing test output — everything stays inside this PC. API key management, proxies, billing logs, and training-reuse concerns simply don't exist
  • Speed is a trade-off you can accept: the calculation is whether 8 tok/s is a fair price for "getting help on work you can't send out"
  • Supervision still applies: you don't hand it off completely (small models sometimes rewrite things outside the instructed scope — measured). Use it as "an assistant whose work a human reviews"

Honest limitations

  • There is no "ask and get a diff back in seconds" experience like the web versions
  • Even a one-off ~10-line generation takes tens of seconds
  • Running the agent loop pegs the CPU (capping inference threads is mandatory)
  • 4B-class models hallucinate and misread often enough that they can't be trusted unsupervised

Summary

A local LLM is not "a substitute for the web versions." It's a slow but real assistant for work that can't leave the building.

What matters is model selection and the design of the tool around it (the harness). In this experiment, gemma4:e4b plus an appropriate harness completed autonomous coding tasks even in a CPU-only environment.

How much that "harness design" controls success — in fact, how my own harness bug looked exactly like "model weakness" — is the next article's story.
